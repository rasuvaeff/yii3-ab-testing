# Матрица интеграций

У каждого пакета семейства есть хороший изолированный пример. Этот документ
добавляет то, чего не хватает между «понял идею» и «запустил в проде»: ответ на
вопрос **«как собрать именно мою комбинацию»**.

Прочитать один раз, выбрать по одному варианту на каждой оси — остальное
следует само.

---

## Ось 1 — где живут определения экспериментов

| Вариант | Ставить | Когда |
|---|---|---|
| PHP-конфиг | только ядро | определения всё равно меняются деплоем |
| База данных | `yii3-ab-testing-db` | нужен kill switch и переразвеска без деплоя |

**Биндить `ExperimentProvider` может ровно один источник.** Установить db-бэкенд
и при этом привязать `ConfigExperimentProvider` в приложении — это ошибка
`yiisoft/config` `Duplicate key`, и она осознанная: баг здесь не в сообщении, а
в двух источниках истины об экспериментах.

```php
// только конфиг: биндит приложение
ExperimentProvider::class => static fn (): ExperimentProvider
    => new ConfigExperimentProvider($params['experiments']),
```

С db-бэкендом не биндить ничего — ключ принадлежит пакету.

## Ось 2 — как события доезжают до аналитики

| Вариант | Ставить | Компромисс |
|---|---|---|
| **Durable** | `yii3-ab-testing-outbox` + `yii3-outbox-db` + воркер | переживает недоступность аналитики; стоит таблицы и запущенного воркера |
| **Log-shipping** | logger-синки ядра + Vector/Fluent Bit | без воркера и без сетевого вызова в запросе; доставка — забота коллектора |

Оба дают **одинаковые строки** в одних и тех же таблицах схемы v2, которыми
владеет `yii3-ab-testing-clickhouse`.

**Не писать в аналитическое хранилище из запроса.** Под PHP-FPM вставка на
каждый запрос — это множество мелких записей плюс сетевой вызов внутри
пользовательской latency; именно поэтому прямой писатель в ClickHouse удалён
в 2.0.

Durable — когда потеря событий недопустима и воркеры уже есть. Log-shipping —
когда лог-конвейер уже есть, а очередь заводить не хочется.

## Ось 3 — кто такой субъект

| Вариант | Как | Когда |
|---|---|---|
| Анонимная кука | `SubjectIdMiddleware` (`yii3-ab-testing-web`) | публичный трафик без логина |
| Авторизованный id | ваш auth-middleware пишет request-атрибут | залогиненные пользователи; куки-ветка не задействуется |
| Гибрид | оба плюс `AnonymousToAuthenticatedStrategy` | посетитель логинится посреди эксперимента |

У гибрида есть ловушка, которую стоит назвать: без стратегии переноса посетитель
после логина получает **другой** вариант, потому что сменился subject id.
`MigrateAssignments` переносит назначение.

## Ось 4 — закрепление варианта

| Вариант | Ставить | Переживает |
|---|---|---|
| Ничего | — | ничего: смена весов перераспределяет всех |
| Подписанная кука | `yii3-ab-testing-web` | переразвеску; **не** чистку кук и не смену устройства |
| База данных | `yii3-ab-testing-db` (`DbAssignmentStore`) | переразвеску, устройства, чистку кук |
| Своё | реализовать `ConfigurationAwareAssignmentStore` | — |

Назначение детерминировано от `(salt, subjectId)`, поэтому субъект сохраняет
вариант, **пока держатся веса**. Меняются веса — двигаются границы бакетов.
Если эксперимент когда-нибудь будут переразвешивать на ходу (а будут), стор не
опция.

## Ось 5 — несколько sink'ов сразу

Каждый tracker-ключ принадлежит одному источнику. Для веера — composite в
собственном конфиге:

```php
ExposureTracker::class => static fn (): ExposureTracker => new CompositeExposureTracker(
    new OutboxExposureTracker(/* … */),
    new LoggerExposureTracker(/* … */),
),
```

Два пакета, биндящих `ExposureTracker`, дают `Duplicate key`. С 2.0
`yii3-ab-testing-clickhouse` не биндит ни один, так что эта конкретная коллизия
исчезла.

## Ось 6 — SSR или SPA

В SSR сервер знает, что отрендерил вариант. В SPA это знает **только клиент** —
и это меняет одну вещь принципиально.

| | SSR | SPA / headless |
|---|---|---|
| Идентичность | кука | request-атрибут из токена либо клиентский id заголовком |
| Cross-origin | не возникает | `SameSite=None` + `Secure` + CORS с credentials |
| Закрепление | куки-стор | `DbAssignmentStore`, если куки исключены |
| **Показ** | на сервере, при рендере | **вызов, который делает клиент** |

Никогда не трекать показ на эндпоинте, отдающем назначения: туда попадут
префетчи, роуты, до которых не дошли, и каждая повторная навигация.

Три эндпоинта, и они принадлежат приложению — роутинг, авторизация и rate
limiting не дело библиотеки:

```
GET  /ab/assignments   → варианты + подписанный receipt, без трекинга
POST /ab/exposure      → клиент отрисовал
POST /ab/conversion    → цель достигнута
```

Receipt обязан быть подписан (`SignedReceiptCodec`). Перерезолв на сервере не
замена: после переразвески он вернёт вариант, который посетитель **получил бы
сейчас**, а не тот, который видел.

Исполняемый пример:
`vendor/rasuvaeff/yii3-ab-testing-web/examples/spa-endpoints.php`.

## Ось 7 — эксплуатация

**Миграции.** Документированная регистрация через `setSourceNamespaces()` молча
не находит ничего, пока установлено ядро: `migrate:up` печатает «up-to-date»,
возвращает 0 и не создаёт таблиц. Применять через `Injector` — см. `UPGRADE.md`
каждого `-db` пакета.

**Воркер** (только durable-путь) дренирует outbox: `outbox:clickhouse:export`.
Без него события копятся и до аналитики не доезжают — smoke-тест reference app
проверяет именно количество доставленных строк, потому что HTTP 200 здесь ничего
не доказывает.

**Retention** — opt-in SQL в `yii3-ab-testing-clickhouse/retention/`, никогда не
применяется автоматически.

**Удаление данных.** `subject_id` — персональные данные, когда это user id.
`DbAssignmentStore::forget($subjectId)` стирает субъекта по всем экспериментам.

## Ось 8 — чтение результатов

```sql
SELECT variant, uniqExact(subject_id) AS subjects
FROM ab_exposures_v2 FINAL
WHERE experiment = 'checkout_button' AND decision_reason = 'assigned'
GROUP BY variant
```

Два обязательных условия:

- **`FINAL`.** Дедупликация происходит при мерже, а не при вставке, доставка —
  at-least-once. Без него повторная доставка считается дважды.
- **`decision_reason = 'assigned'`.** Forced-трафик (QA) и оба вида fallback
  участием в эксперименте не являются.

Правила атрибуции — окно, повторные конверсии, исключения — зафиксированы в ядре
(`AttributionWindow`, `RepeatedConversionPolicy`), чтобы любой бэкенд отчётности
отвечал одинаково.

| 2.x | 2.x | 3.x | 2.x | 2.x |
